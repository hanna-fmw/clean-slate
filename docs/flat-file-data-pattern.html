Yes - and it's a legit, well-known pattern, not a hack. It's sometimes called a flat-file / git-as-data / build-time data approach. The rule of thumb for when it fits:

Good fit (use this instead of a database):

  • The data only changes occasionally, and only you (or a trusted few) change it
  • The app only ever reads it - users don't create or edit data through the app
  • It's small-to-moderate in size
  • A little lag is fine (updates appear after the next sync + redeploy, not instantly)

That's exactly Clean Slate, and it's also how blogs, docs sites, portfolios, changelogs, pricing pages, "team" pages, etc. are usually built.

Needs a real database instead:

  • Users submit or edit data in the app (forms, logins, comments, orders)
  • You need instant updates or many people writing at once
  • You need to query/search/filter large or related datasets live

The three pieces are also swappable - don't think of launchd as the only way:

  • The scheduler (launchd) is just "run this every N hours." You could instead trigger on file change (so it updates seconds after you edit, not on a 6-hour timer), run it manually, or use a scheduled GitHub Action in the cloud so it doesn't depend on your Mac being on.
  • The delivery (commit JSON → deploy) is one option. You could also write the JSON to a storage bucket the app reads, or regenerate it as part of the build step so every deploy is fresh.

So yes: any time the answer to "where does this data come from?" is "a folder on my computer that I update now and then," this pattern is usually the right, cheapest tool - no database, no hosting cost, nothing to secure. The moment the answer becomes "users type it into the app," that's your signal to reach for a database.
